4What reaches the LLM is verified

Validated going in, typed coming back

Everything the founder sends is validated by Pydantic before any model call. Everything else is built by code from typed data or passes through the guardrails, and all of it is fenced.

What goes to the modelHow it is checked
The founder's brief, answers, follow-ups, questions and instructionsA Pydantic request model with limits (a brief of up to 8,000 characters, at most 10 answers and 50 sources), then the guardrails. Anything else: 422, and no model call.
Uploaded filesNot Pydantic, since the body is the file's bytes. The extractor checks the size (10 MB), the real file type, and page, row and character limits; only the text is kept, then the guardrails.
Web results (Bing, Tavily)Typed records, snippets cut to length, then the guardrails. Free text: Pydantic cannot judge it.
FRED figuresBuilt into Pydantic Figure models; the values worked out in code.
Decisions passed between agentsPlans, reviews and conflicts are Pydantic-validated before they are used.
Reports read by other agentsProse, fenced as another agent's report.
Competitor profilesThe one loose spot: each field becomes text before its model, so a malformed field passes as text. Still fenced.
Pydantic checks shape and size, not safety. The guardrails check content: invisible characters removed, attempts to instruct the agents cut out, the rest fenced, and every system prompt says fenced text is material, not orders.

On the way back: the model's replies

  • 17 of 22 prompts answer in a strict JSON schema made from a Pydantic model, and the reply is validated again.
  • 5 are prose by design: the four reports and the strategy.
  • Gap 1: ranges live in field descriptions, so a review scored 9 would pass. Fix: validators, with a test each.
  • Gap 2: a reply that breaks the schema is not retried (a 500; rare under strict mode). Fix: catch it in structured_invoke, retry once, then treat it as unusable.
