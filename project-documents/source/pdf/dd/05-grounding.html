Before the team starts: research the brief, and ask what only the founder knows

  1. A template, if wanted. Five decision templates (evaluate a new idea, plan the go-to-market, set the price, get ready to raise, respond to a competitor) each give a brief to fill in, what that kind of decision needs looked up, and what the Chief of Staff must know.
  2. Search. A structured call writes two to four web searches (SearchPlan; code keeps four at most). They run at once on Azure OpenAI's Bing search, the default, or on Tavily, as the sidebar chooses, and each page is kept once.
  3. Read. The Chief of Staff reads the brief with the numbered results (BriefReview): up to eight facts, each citing the results it came from, and up to three questions, only about facts only the founder knows (budget, team, traction, goals), never a choice the team is there to make. Code drops any fact that cites no real result, and renumbers the sources in order of first citation.
  4. Review. The founder leaves out any fact that does not fit, and answers or skips each question. The answers and the facts kept travel with the request to every agent; the specialists cite them as [n], and the report gains a Web Research section with the sources.

With no research provider set up, or when every search fails, the brief is still checked, and a note says why there is no research. The founder's brief, and every page the searches return, pass through the guardrails.

5.2Grounding the work in evidence

Deep research: a cited report for each specialist, and profiles of the competitors

With Deep research switched on, a research step runs after the plan, beside the look-ups. A structured call names up to three real competitors (Competitors, capped at three in code). Then, all at once, one research task runs for each assigned specialist's area, written from its task and the founder's brief, and one for each competitor, answering in a fixed profile: summary, pricing, customers, funding, recent moves, strengths, weaknesses.

Each report numbers its own sources from 1. A source book gives every page one number for the whole session, after the brief's research, and renumbers the citations to match, so a specialist's [12], the strategy's and the report's all mean the same page.

Each specialist reads its own area's report; Marketing and Finance, who price and position against them, also read the competitor profiles. A follow-up reuses the session's research. A task that fails leaves its area out and is listed as not researched; it never fails the request.

With deep research on Tavily, each competitor's own pricing page is also found and read through Tavily's MCP server, and quoted in its profile with its source.

5.3Grounding the work in evidence

Official figures through the app's own MCP server, exact and cited

The server. fred_server.py is a Model Context Protocol server with two tools, search_series and series_data, whose results are Pydantic models. The API starts it as a subprocess and speaks to it over stdio; of the API's settings, only the FRED key reaches it, and it cuts the key out of the request lines it logs.

Planned look-ups, not a tool loop. After the plan, the Chief of Staff names up to four FRED searches for the figures the decision turns on. Code lists the current series that cover each one; the Chief of Staff picks up to four that fit the venture's market and place, saying why; ids it was not offered are dropped. The 10-year Treasury yield and consumer prices are always read. Code then works out each series' latest value and its change over the year.

Read by every specialist, fenced as data, cited as [FRED · DGS10], and kept for the session's follow-ups. The look-up runs beside deep research, and the specialists start once both are done. If FRED is down, as it is during maintenance, the figures are left out with a note and the run goes on.

Why planned look-ups? The time, the cost and the figures stay predictable: the Chief of Staff decides what to look up, code fetches it and does the sums, and the specialists read the result.

5.4Grounding the work in evidence

The founder's own documents in, and cited answers out

Reading a file

PDF, Word, PowerPoint, Excel, OpenDocument, CSV, RTF, HTML, Markdown and text. The type is told from the content (a PDF's header, an Office file's parts), never from the name; an older Office file, an image or a password-protected PDF is refused with the reason.

Read within limits: 10 MB, an archive's unpacked size and ratio (against zip bombs), XML through defusedxml, 400 pages, 5,000 rows a sheet, 400,000 characters. Only the text is kept, in passages of about 1,500 characters that each say where they are: "page 3", "slide 2", "sheet Revenue, rows 2–41".

Each agent reads its share

A request can name up to five uploads and five earlier reports. For each agent, the passages are ranked by BM25 against its own work (a specialist's task and role, the Chief of Staff's venture and request) within 9,000 characters: each document first gets an equal share, so a long report cannot crowd out a short file.

The passages are fenced as the founder's material, and every agent cites what it uses by the passage's mark. The report records the documents the run worked from; a follow-up keeps them.

Questions, answered from the documents

"Ask about it" puts a question to a report, the files its run worked from and any others: the passages that bear on it, within 14,000 characters, go to the Chief of Staff, which answers from them alone and cites each.

The answer is a typed reply (Answer: the text and the marks it cites); code matches each mark back to a real passage, so the response lists only what it really cites and drops any mark the model made up.
