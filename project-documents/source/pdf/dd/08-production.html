8.2Production readiness

Nothing lost on a restart, and nothing open that should not be

Persistence: PostgreSQL
or memory, without DATABASE_URL, as the tests run
  • SessionsLangGraph's AsyncPostgresSaver, built on the event loop that serves requests, so a follow-up after a restart starts from the session's state.
  • ReportsOne row a session. A change reads it FOR UPDATE, applies it and writes it in one transaction, so a save from an older version is refused, even with several workers; the replaced version goes to report_versions, the last 30 kept.
  • UploadsThe text read from each file, never the file; the newest 500.
  • The Monitor's historyWritten in batches by a thread of its own: the latest 1,000 evaluations and 10,000 events; read back on start.
  • MigrationsNumbered, applied under an advisory lock so two workers starting together do not both migrate. With a database set, the API will not start without it, rather than quietly forget.
Security and limits
checked before any route, security.py
  • The keyWith API_KEY set, every route but /health needs it, compared in constant time. The browser never holds it: the app's server adds it.
  • SizeA body over 1 MB is refused (413), whether or not it says how big it is; an uploaded file may be up to 10 MB.
  • Rates300 requests a minute and 30 runs an hour per caller, over sliding windows; at most 4 runs at once, each holding its place until its response ends. Over a limit: 429 with Retry-After.
  • Who a caller isIts address, or, only for a request carrying the key, the browser address the app's proxy forwards, so nobody can spread their requests over made-up addresses.
  • What is loggedNo brief text: a failed search logs its error, not the query.
  • The pagesA content security policy, no framing by other sites, a strict referrer policy. TLS belongs to the reverse proxy in front.

8.3Production readiness

Observability: every request traceable, every step measured

Request IDs. Each request gets an ID (the one it sent, if usable), returned in X-Request-ID and stamped on every log line about it, with its session. The threads that run the agents copy the context, so their lines carry the ID too, and a founder's "it failed" leads straight to the right lines.

Logs. One line a request, with the route's template, status and time; as text, or as one JSON object a line with LOG_FORMAT=json. The polled routes log at DEBUG; an unexpected error is logged with its traceback.

The Monitor. Since the API started: evaluations ended and running, briefs and proposals, requests and server errors, the median and 95th-percentile time of an evaluation and of each step, model calls, tokens, reviews, conflicts and research cost, and the last 300 events. Health turns to errors if one was logged in the last 15 minutes.

Prometheus. The same as counters and histograms at /metrics (cofounder_*), routes labelled by template so no session ID becomes a label.

8.4Production readiness

Langfuse: what each agent was asked and answered, at what cost, and how well

Traces, masked

Each request that calls a model is one trace (evaluate, brief, proposal, revisions, questions), grouped by session and tagged. Inside it, every model call is a generation with its messages, reply, model, tokens, cost and time.

No call site passes a handler: while a trace is open, LangChain picks Langfuse's handler up from the request's context, in every worker thread.

Before anything leaves, emails, phone numbers, card numbers (by the Luhn check) and keys become [email], [phone], [card number], [key]. Without Langfuse's keys, nothing is traced and nothing leaves.

Prompts, versioned from the code

The code is their source. At start-up each of the 22 prompts is registered, as a new version labelled production only when its text has changed, and every call is linked to the version it used, so versions can be compared on cost, speed and scores.

Scores on every run

The team's own judgements: review-marketing and the others, review-average, approved-first-time, revisions, conflicts, the verdict, failed-specialists, guardrail-flags; and the founder's founder-feedback.

An LLM judge

With LANGFUSE_JUDGE on, after the answer has gone, a separate call scores the strategy from 1 to 5 on constraints, consistency, actionability and grounding, with what lowers them most.

Experiments

The example scenarios are the cofounder-scenarios dataset. One command runs the team on each, traced and scored by the team and the judge, so a change to a prompt or a reasoning effort is compared run against run:

uv run python experiments.py \
  --name "chief at low" --chief low
Checked live in Step 35, on the team's Langfuse Cloud project (EU): at start-up the API registered the 22 prompts; a real evaluation of 141 s was one trace of 20 model calls, each a generation with its model, tokens and cost and linked to its prompt's version; the team's scores and the founder's verdict sat on the trace, the founder's email masked to [email].

One command to run it, here or in containers; the same checks on every push

One launcher
start.sh
./start.sh          # asks how
./start.sh local    # API + web here
./start.sh docker   # in containers
./start.sh stop

Locally it starts the API and the web app on 127.0.0.1, hands the web app's server the API's address and key, labels each server's lines and stops both together. It offers the next free port when one is taken, and asks before creating a database password.

No credentials, no model calls

The tests swap in a fake model, which returns a typed reply for each schema (a plan, a review, a critique…) that a test can replace and echoes the prose calls, and fake MCP servers in the same process; the frontend's tests use a fake backend. The real ones refuse, so no test leaves the machine. Real keys in .env are stripped before any test runs.

What they cover

Delegation, review, critique, follow-ups, streaming, error paths and resilience, guardrails, security limits, persistence through a restart of the API, the proposal's arithmetic, document conversions, extraction, look-ups, tracing and the launcher, among 30 backend test files.

Then live, against Azure OpenAI

The steps were also checked live: 34 checks are recorded in the development plan, many in headless Chrome, light, dark and at phone width. The live runs found what fakes could not (a planner assigning too few specialists, figures that did not add up) and each fix came with a test.
